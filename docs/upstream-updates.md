# Upstream Updates

How to pull framework improvements into your brain instance.

## Setup

Add the Almagest framework as an upstream remote (one-time):

```bash
git remote add upstream <almagest-framework-repo-url>
```

## Pulling updates

```bash
git fetch upstream
git merge upstream/main
```

## What merges cleanly

| File type | Why it works |
|-----------|-------------|
| `brain/rules-index.md` | You didn't edit it — upstream's version replaces yours |
| `agent/contract.md`, `agent/rules/*` | Framework-owned. Generic logic; your customization is in `brain.config.yaml` |
| `tools/agent-shims.sh`, `tools/audit.mjs` | Framework-owned. Check IDs (`CITE-002`, `LINK-001`, …) are stable, so a new upstream check shows up as new findings, not renamed ones |
| `package.json` (root) | Framework-owned — it exists to run the audit |
| `.github/workflows/*` | Framework-owned — unless you added jobs of your own (see below) |
| `benchmarks/drivers/*` | Framework-owned — unless you wrote a driver of your own (see below) |
| `site/src/components/*` | Framework owns components, you only customize `theme.css` |
| `site/src/lib/wiki.ts` | A typed wrapper over `tools/lib/wiki-core.mjs`; it parses nothing, so it rarely conflicts |
| `tools/lib/wiki-core.mjs` | The one wiki parser, shared by the site and the audit — unless you edited `WIKI_DIRS` for multi-brain (see below) |
| `site/package.json` | Framework owns the dependency set |
| `site/src/layouts/*` | Same — framework-owned |
| `site/src/pages/*` | New pages add cleanly, existing pages update |
| `site/src/styles/base.css` | Framework design system — your overrides are in `theme.css` |

## What never conflicts

| Path | Why |
|------|-----|
| `brain/wiki/*` | Upstream ships only `_example.md` — your content is yours |
| `brain/raw/*` | Upstream ships only `.gitkeep` |
| `brain/raw/extracted/*` | Upstream ships only `.gitkeep`. Your sidecars are committed and yours |
| `brain/.index/*` | Generated from your pages. Upstream's is empty — see below |
| `brain/canonical-challenges.md` | Your rejected-data log, upstream's is an empty template |
| `brain/manifest.yaml` | Your ingest record, upstream's is an empty template |
| `brain/index.md` | Your catalog, upstream's is empty template |
| `brain/log.md` | Your audit trail, upstream's is empty template |
| `brain.config.yaml` | Your config, upstream ships example values |
| `site/src/styles/theme.css` | Your theme, upstream ships it empty |
| `site/site.config.ts` | Your site config |
| `site/dist/`, `site/node_modules/` | Gitignored |

## Generated files

`AGENTS.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.claude/rules/*`, `.cursor/rules/*`, and `brain/CLAUDE.md` are generated from `agent/rules/` by `tools/agent-shims.sh`. They are committed, so a rules change upstream shows up as a diff in all of them at once.

If one conflicts, do not merge it by hand:

```bash
git checkout --theirs <file>   # take upstream
tools/agent-shims.sh generate  # then regenerate everything
tools/agent-shims.sh check     # exits 1 if anything is still out of sync
```

## The derived index

`brain/.index/pages.tsv` and `aliases.tsv` are generated by `tools/audit.mjs
index` and **committed**, the same idiom as the shims. Same conflict rule
applies, and the same fix: never resolve them by hand.

```bash
node tools/audit.mjs index         # regenerate from your pages
node tools/audit.mjs --check-index # exits 1 if the files are stale
```

Because they are derived, a conflict in them is always noise — it means both
sides regenerated from different page sets. Take either side, then regenerate.
The output is deterministic (sorted by slug, tab-separated, no timestamps), so
after regenerating the file is byte-identical for anyone with the same pages.

A conflict in the *format* of the index — an upstream column added or renamed —
resolves the same way: take upstream, regenerate. Do not carry your old columns
forward; the site and the query protocol read the new shape.

## What might conflict

If you've edited a framework-owned file, the merge will show a conflict. This is the right behavior — you see exactly what upstream changed and decide how to integrate.

The most likely one is `tools/lib/wiki-core.mjs` if you added brains to `WIKI_DIRS`. Keep your array, take upstream's everything-else — and take it carefully: that file is the single parser behind both the site and `tools/audit.mjs`, so a bad resolution there breaks rendering and checking at once. Two invariants to preserve while resolving it: it imports **no packages** (`gray-matter` and `marked` arrive by injection, so that `cd site && npm install && npm run build` works with no root install), and it stays `.mjs`, because bare Node 22 cannot import TypeScript. The second most likely is a rule file you edited in place — move the edit into `brain.config.yaml` if it is instance-specific, or keep it and expect it back at every merge. The third is `.github/workflows/ci.yml` if you added a job (a per-brain audit step, for instance): keep your job, take upstream's audit and shim-check steps verbatim.

### Resolving conflicts

```bash
# After merge conflict:
git diff          # see what conflicted
# Edit the file to combine your changes with upstream's
git add <file>
git commit
```

## Recommended workflow

1. **Pull regularly** — small, frequent merges are easier than big ones
2. **Don't edit framework files** unless you have to — put customization in config
3. **Review the diff** before merging: `git diff upstream/main`
4. **Test after merge**, in this order:
   ```bash
   tools/agent-shims.sh check     # shims in sync with agent/
   node tools/audit.mjs           # exit 1 means upstream added a check your pages fail
   node tools/audit.mjs index     # regenerate, then commit the result
   cd site && npm run build
   ```
   An upstream merge that adds a check is the normal way new findings appear on
   old pages. They are real findings, not merge damage: fix the pages. Nothing
   in Almagest rewrites your content to satisfy a new check, and you should be
   suspicious of anything that offers to.
